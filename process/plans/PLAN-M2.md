# Milestone M2: Portfolio and Allocation tabs

## Scope

Build the app shell (header, tabs, CTA) and the first two functional tabs — Portfolio and Allocation — so a user can assemble a portfolio of consumers and generators (from the built-in library or a CSV upload), define an allocation matrix and matching granularity, and see a persistent score strip with live hourly and annual scores computed by the engine. A demo portfolio loads on first visit so the score strip shows numbers immediately. All state is persisted to localStorage.

## Out of scope

- Results charts and detailed results view (M3)
- Saving/loading scenarios, Compare tab content, PDF export, HubSpot gate (M4)
- Design polish beyond correct use of tokens, accessibility pass, Vercel deploy (M5)
- Any backend or API calls
- Scenario JSON import/export

## Notes for the generator

1. **IO layer is already built.** `src/io/profileUpload.ts` and `src/io/timestamps.ts` already implement CSV parsing, timezone conversion, half-hourly aggregation, DST handling, leap-day dropping, and gap rejection, with comprehensive tests in `src/io/__tests__/profileUpload.test.ts`. Wrap them in the upload UI; do not rewrite them.

2. **Engine is complete.** `src/engine/` passes golden-fixture parity tests. Import `runEngine` from `src/engine` and run it with `useMemo` whenever the portfolio, matrix, or granularity changes. The engine must stay under 50 ms for a 5 × 5 portfolio.

3. **Demo scenario sizing.** The demo uses non-default sizing: solar PV temperate at **25 MW** (not the registry default of 20) and onshore wind temperate at **10 MW** (not 20). This matches the golden fixture `single-consumer-solar-wind`. The generator's annual MWh = capacityMW × capacityFactor × 8 760 (solar: 25 × 0.11 × 8 760 = 24 090; wind: 10 × 0.30 × 8 760 = 26 280).

4. **Score strip at hourly granularity.** With hourly matching, every hour's allocation equals its matched energy (min of supply and demand per hour), so `annualScore === hourlyScore`. Both being 67.33 % is correct, not a bug.

5. **Feedback items from FEEDBACK.md.** Priya noted that annual score should sit clearly beside hourly score, not buried elsewhere. The score strip must label both "Hourly matching score" and "Annual matching score" (or equivalent) so the relationship is clear. Samuel's timezone feedback is addressed by the timezone picker in the upload flow.

6. **Profile shapes.** Library profiles are normalised JSON arrays (sum ≈ 1.0) loaded from `src/data/profiles/<file>`. Scale them: consumer demand = shape[h] × annualMWh / Σshape; generator output = shape[h] × capacityMW × capacityFactor × 8 760 / Σshape.

7. **Sample CSVs.** Generate two files in `public/samples/` (e.g. `sample-consumption.csv` and `sample-generation.csv`) with ISO naive timestamps (2025-01-01 00:00 to 2025-12-31 23:00), one value column, hourly, UTC. Values should produce a recognisable shape (not all zeros or all ones).

8. **Allocation matrix.** The project plan specifies: "each generator's output split across consumers; column total per generator ≤ 100 %". Generators are rows, consumers are columns. The row total is what is capped at 100 %, not the column total — the matrix tracks how each generator distributes its output.
